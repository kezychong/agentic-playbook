# Generation — Produce the Actual Deliverables

The skill's value is producing real, usable assets — not describing them. Generate each as its own file in the user's project folder, reading from their `audience.md` and `offer.md` so everything is niche-specific. Never leave a deliverable as a placeholder or a summary.

Legend: **[CORE METHOD]** = the supplied method. **[RESEARCHED]** = credited structure.

## 1. Challenge outline (day-by-day arc)

The spine of the whole product. **[CORE METHOD]** one video + one action per day, building toward the named outcome.

Structure each day as:
- **Day N — [title]**
- **The one action** (the single thing the participant does — never more than one).
- **The daily win** (what they'll have/feel by end of day).
- **Video focus** (what the live teaches).
- **Community prompt** (what they post as proof).

**[RESEARCHED] Arc shape** to sequence the days:
- **Day 1 = quick win + proof post + identity shift** (*Scale For Impact*), never an overview.
- Middle days = build the framework, one action at a time.
- **[RESEARCHED — 5-day sprint model]** if short-format: quick win early → teach the framework → **"offer day" near the end**.
- **[RESEARCHED — 30-day format]** if running 30 days: weekly themes (e.g. Week 1 foundations, Weeks 2–3 build, Week 4 push), a mission each weekday.
- **[RESEARCHED — 6-week format]** if running longer (6 weeks / 42 days): 2 foundation days, then a long daily-drop stretch to the finish.
- Seed the back-end offer before the final day (see `funnel-design.md` timing).

Produce the full outline for the chosen duration — every day filled, no "…and so on."

## 2. Launch content calendar (the runway)

**[CORE METHOD]** the tease-tease-tease runway. Map every pre-launch touch to a date relative to the start:

| When | Asset | Job |
|------|-------|-----|
| T-14 to T-10 | Tease posts | "Something's coming" — hint the outcome |
| T-7 to T-4 | Warm-up posts | Who it's for, what they'll get |
| T-4/T-3 | **Formal announcement** | What/who/outcome/format/start date/how to enroll |
| T-3 to T-1 | Enrollment push | "Spots filling — cart closes [date]" |
| T-1 | Final cutoff call | Last chance before the cohort locks |

Write actual post/email copy for each slot in the user's voice — not just labels. **[RESEARCHED]** keep the dated scarcity plain and true; no fake countdowns.

## 3. Registration-page brief

This is a brief for whoever builds the actual registration page — not the finished page. Write it as real content for each block (not just headings), so it's a ready handoff:
- **Headline** — the challenge name (outcome + timeframe).
- **Subhead** — the promise / who it's for.
- **What you'll do each day** — the daily-action rhythm.
- **What's included** — live videos + replays + community + any workbook.
- **The dated scarcity** — start date + enrollment cutoff, stated plainly.
- **Proof** — real results/testimonials from intake (never fabricated).
- **Price + CTA** — the offer and one clear button.
- **[RESEARCHED — optional]** a VIP upgrade block (see `funnel-design.md`).

## 4. Daily prompts

For each day, the participant-facing prompt: the one action, why it matters today, and the community check-in ("post your [proof] in the group"). **[RESEARCHED]** pair each with a short written action sheet (a "one-pager" pattern) so people can complete without rewatching.

## 5. Upsell pitch outline

**[CORE METHOD]** the end-of-challenge transition into the fulfillable offer. Outline:
- **The bridge** — connect the win they just got to the bigger transformation they still want.
- **The reveal** — the coaching/group/membership offer, framed as the natural next step (not a bolted-on pitch).
- **Why now** — the momentum they've built + a real reason to decide.
- **The CTA** — how to enroll, with any cart window/bonus.

**[RESEARCHED]** avoid the classic failure of a rushed last-day 10-minute pitch; seed the offer earlier (60% Rule / bridge day).

## Delivery rules

- One file per deliverable, all in the user's project folder.
- Everything reads from `audience.md` + `offer.md` — specific to their niche, never generic.
- Plain English, the user's voice, no AI-slop phrasing (no em-dash drama, no "it's not X, it's Y").
- Tag any element drawn from researched best practice with its named source so the user knows what's the core model vs. added structure.
